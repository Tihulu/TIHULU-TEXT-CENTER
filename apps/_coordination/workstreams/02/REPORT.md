### 1. Exact app-owned versus external service semantics

1. **Current main `control.py`:** `UNITS=("readsb.service","tar1090.service")` and `service_action(start|stop|enable|disable)` dispatch paired `sudo -n /usr/bin/systemctl <action> readsb.service tar1090.service` ([tihulu_flight_radar/control.py L13–17](https://github.com/Tihulu/tihulu-flight-radar/blob/059b391280635d9aa4d2ac73c7318af9e135ebf5/tihulu_flight_radar/control.py#L13-L17), [tihulu_flight_radar/control.py L88–116](https://github.com/Tihulu/tihulu-flight-radar/blob/059b391280635d9aa4d2ac73c7318af9e135ebf5/tihulu_flight_radar/control.py#L88-L116)). `start()` sets `_service_started_by_app=True` when readsb was initially inactive, but `close(release_local_service=False)` **ignores** the ownership flag and leaves Linux services; `close(True)` stops both if readsb is currently active, **even if it was pre-existing** ([tihulu_flight_radar/control.py L156–164](https://github.com/Tihulu/tihulu-flight-radar/blob/059b391280635d9aa4d2ac73c7318af9e135ebf5/tihulu_flight_radar/control.py#L156-L164), [tihulu_flight_radar/control.py L234–263](https://github.com/Tihulu/tihulu-flight-radar/blob/059b391280635d9aa4d2ac73c7318af9e135ebf5/tihulu_flight_radar/control.py#L234-L263)). Default persistent Qt checkbox `release_sdr_on_exit=True` ([tihulu_flight_radar/app.py L313–333](https://github.com/Tihulu/tihulu-flight-radar/blob/059b391280635d9aa4d2ac73c7318af9e135ebf5/tihulu_flight_radar/app.py#L313-L333)). This is preference-controlled *paired-service* close, **not owner-only cleanup**. UI's informational text that existing services remain active is not an unconditional guarantee.
2. **Draft #7 `control.py`:** if readsb is already active, `start()` returns **without issuing `service_action` or taking ownership**. An inactive readsb started by app sets `_started_service_in_app=True`. `close()` unconditionally stops an app-owned direct readsb child; stops systemd readsb **only if the ownership flag is set**, using narrow single-unit `sudo -n /usr/bin/systemctl stop readsb.service`; it leaves `tar1090.service` untouched on automatic exit and keeps originally active external readsb untouched ([tihulu_flight_radar/control.py L101–120](https://github.com/Tihulu/tihulu-flight-radar/blob/4ef8245b87fc78cec6cc4f5f9043d68e08cf45d3/tihulu_flight_radar/control.py#L101-L120), [tihulu_flight_radar/control.py L162–170](https://github.com/Tihulu/tihulu-flight-radar/blob/4ef8245b87fc78cec6cc4f5f9043d68e08cf45d3/tihulu_flight_radar/control.py#L162-L170), [tihulu_flight_radar/control.py L240–259](https://github.com/Tihulu/tihulu-flight-radar/blob/4ef8245b87fc78cec6cc4f5f9043d68e08cf45d3/tihulu_flight_radar/control.py#L240-L259)). **Explicit Stop and Restart still invoke the paired service command** through `service_action("stop")` ([tihulu_flight_radar/control.py L70–98](https://github.com/Tihulu/tihulu-flight-radar/blob/4ef8245b87fc78cec6cc4f5f9043d68e08cf45d3/tihulu_flight_radar/control.py#L70-L98), [tihulu_flight_radar/control.py L204–217](https://github.com/Tihulu/tihulu-flight-radar/blob/4ef8245b87fc78cec6cc4f5f9043d68e08cf45d3/tihulu_flight_radar/control.py#L204-L217)). “Never stop an external service” is therefore only an **automatic-close** rule, not a blanket claim about user-requested Stop/Restart.
3. **Both:** Direct mode rejects starting while Linux `readsb.service` is active; app-started direct child is terminated/waited (forced kill on timeout), with own temporary directory cleanup; Remote JSON cannot Start/Stop and does not manage external service on exit ([tihulu_flight_radar/control.py L165–223](https://github.com/Tihulu/tihulu-flight-radar/blob/059b391280635d9aa4d2ac73c7318af9e135ebf5/tihulu_flight_radar/control.py#L165-L223), [tihulu_flight_radar/control.py L171–229](https://github.com/Tihulu/tihulu-flight-radar/blob/4ef8245b87fc78cec6cc4f5f9043d68e08cf45d3/tihulu_flight_radar/control.py#L171-L229)). `tar1090` is a map/backend viewer service, **not evidence of exclusive USB ownership**.
4. **Close and errors:** Main `app.py` stops the UI timer/map server first, calls `controller.close(release_checkbox)` only when `_owns_receiver` is true, warns on `DataError`, **then completes window close** without confirming SDR release ([tihulu_flight_radar/app.py L731–753](https://github.com/Tihulu/tihulu-flight-radar/blob/059b391280635d9aa4d2ac73c7318af9e135ebf5/tihulu_flight_radar/app.py#L731-L753)). Draft #7 first calls `action_future.result(timeout=35)`, closes the owner, and on `DataError` calls `event.ignore()` with timer restored, allowing explicit retry ([tihulu_flight_radar/app.py L701–724](https://github.com/Tihulu/tihulu-flight-radar/blob/4ef8245b87fc78cec6cc4f5f9043d68e08cf45d3/tihulu_flight_radar/app.py#L701-L724)). **Wait is bounded**; exceptions from the future are swallowed by that wait. Its earlier `RadarWindow()` implementation also lacks main's injectable `controller=None, owns_receiver=True` interface ([tihulu_flight_radar/app.py L141–148](https://github.com/Tihulu/tihulu-flight-radar/blob/059b391280635d9aa4d2ac73c7318af9e135ebf5/tihulu_flight_radar/app.py#L141-L148), [tihulu_flight_radar/app.py L139–146](https://github.com/Tihulu/tihulu-flight-radar/blob/4ef8245b87fc78cec6cc4f5f9043d68e08cf45d3/tihulu_flight_radar/app.py#L139-L146)). Neither draft behavior nor `event.ignore()` has been demonstrated in an installed Qt + SDR test.
5. **Installer compatibility:** The current main sudoers Cmnd_Alias grants paired operations but **not** standalone `systemctl stop readsb.service` ([scripts/install-linux.sh L122–129](https://github.com/Tihulu/tihulu-flight-radar/blob/059b391280635d9aa4d2ac73c7318af9e135ebf5/scripts/install-linux.sh#L122-L129)). Draft #7's older installer adds that exact single-unit command ([scripts/install-linux.sh L55–64](https://github.com/Tihulu/tihulu-flight-radar/blob/4ef8245b87fc78cec6cc4f5f9043d68e08cf45d3/scripts/install-linux.sh#L55-L64)). Consequently a partial adoption of the new controller onto an old installation can **fail cleanup permission**. Conversely, copying the old PR #7 installer/app wholesale would overwrite features present in modern main. No installer or permissions were touched here.
6. **Ownership flags are session markers, not physical lease proofs:** Neither flag authenticates long-running external systemd ownership after an out-of-band stop/restart, nor confirms that `readsb` actually released the kernel device. `readsb active` and `tar1090 active` are systemd states; USB exclusivity, RTL USB error recovery and return to FM/DAB require a later explicitly authorized device-side acceptance test.
